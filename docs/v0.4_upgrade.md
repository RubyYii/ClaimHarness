# ClaimHarness / ProblemBridge v0.4 Upgrade Guide

v0.4 connects ProblemBridge evidence contracts to ClaimHarness and adds explicit project/run governance. The default workflows remain local-first and deterministic.

## What changed

- Every governed ProblemBridge run has a stable `project_id`, a unique `run_id`, `run_identity.json`, and a final `run_complete.json` marker.
- Output lifecycle is explicit: `new`, `resume`, or `replace`. `resume` and `replace` require both an independently supplied project ID and the current run ID, and identity mismatches fail before writing.
- Revision history uses project-bound schema v3, is append-only, locked across processes, hash-chained, and still limited to three rounds per stable target. Legacy v1/v2 histories require explicit migration.
- ProblemBridge writes a schema-v2 `evidence_contract.yaml` that binds `project_id` and content-derived `contract_id`; ClaimHarness can execute it with `--evidence-contract`.
- Invalid or unknown contract rules fail before ClaimHarness creates or cleans an output directory.
- Document intake writes `ocr_quality_report.json` when packaging extraction results. OCR provenance is `derived_text/ocr`, is not strong evidence by default, and routes derived-input claims to source inspection and human review.
- Share ZIPs use a generated-artifact allow-list, exclude `source_files/` and unknown files by default, and contain `share_manifest.json` with exact paths, sizes, and SHA-256 hashes. Including originals requires an explicit UI choice; project-level deletion requires exact project-ID confirmation.
- A deterministic synthetic evaluation gate now reports claim P/R/F1, evidence recall@k, status macro-F1 and confusion matrix, high-risk miss rate, unsafe high-risk decision rate, and abstention rate.
- Windows setup is separated from daily launch. CI installs the tested `.[dev,ui]` set on Linux and Windows. Release builds derive their version from package metadata, verify committed sample provenance, and emit a manifest and SHA-256 file.

## Evidence-contract audit

Generate a ProblemBridge package, then pass its contract into ClaimHarness:

```powershell
.venv\Scripts\python.exe -m problem_bridge align `
  --brief examples/problem_bridge/quality_inspection/problem.md `
  --out outputs/quality_inspection_alignment `
  --project-id quality-inspection-study `
  --mode new

.venv\Scripts\python.exe -m claim_harness run `
  --manuscript examples/lab_report_audit_demo/manuscript.md `
  --tables examples/lab_report_audit_demo/tables `
  --references examples/lab_report_audit_demo/references.md `
  --evidence-contract outputs/quality_inspection_alignment/evidence_contract.yaml `
  --out outputs/lab_report_contract_audit `
  --llm mock
```

`run_manifest.json` records the contract filename, schema version, `project_id`, `contract_id`, size, and SHA-256. It does not embed the contract or an absolute local path. ClaimHarness also rejects a CLI `--project-id` that differs from the contract project, and recalculates `contract_id` from the executable contract content before any output mutation.

## Safe output lifecycle

`new` refuses a non-empty directory. `resume` only continues an incomplete run and requires the exact original workflow/run specification. `replace` verifies the existing identity, preserves unknown/user files and project history, removes the old and newly declared allow-listed generated artifacts plus run-owned snapshot copies (`extracted_tables/` and `source_files/`), and starts a new run ID. Snapshot trees are checked for links and junctions before any prior output is removed.

Newly allocated run folders use a readable workflow prefix plus a short random
token; the authoritative creation time remains in `run_identity.json`. This
leaves more Windows path budget for nested uploaded sources. The UI history is
ordered by the verified UTC identity timestamp, while folders without a
lifecycle identity use modification time and are explicitly labelled `legacy`.

`run_identity.json` stores `workflow_type` and `run_spec_sha256`. The ClaimHarness and ProblemBridge CLI run specifications include the tool version plus the relevant input/configuration hashes, so a different version or specification cannot silently resume the old run. For `resume` or `replace`, supply both the stable project ID and the current `run_id` (shown in `run_identity.json`) as independent confirmations:

```powershell
.venv\Scripts\python.exe -m problem_bridge align `
  --brief examples/problem_bridge/quality_inspection/problem.md `
  --out outputs/quality_inspection_alignment `
  --mode replace `
  --project-id quality-inspection-study `
  --expected-run-id run-0123456789abcdef
```

The completion marker is published last using atomic file replacement. It binds the identity hash to an exact snapshot of all present governed artifacts. Document-intake runs also hash every nested non-symlink file under the allow-listed `extracted_tables/` and `source_files/` directories, so extracted tables and original uploads are covered. Unknown root files remain outside the governed snapshot and are not automatically shared. This makes incomplete or altered runs observable, but it is not a database transaction or a guarantee against storage-device failure.

## Three-round revision records

Each v3 revision record contains the immutable `project_id`, `revision_id`, `parent_revision_id`, base/output artifact SHA-256 values, the previous record hash, and its own record hash. Loading verifies the record's `project_id` against `project_record.json`, so copying a valid chain into another project fails closed. The file is protected with a cross-process lock and an optimistic `expected_history_sha256` check in the Python API.

Legacy v1/v2 histories are not read, appended, or upgraded silently. Migrate one homogeneous legacy history once, explicitly confirming the destination project identity:

```powershell
.venv\Scripts\python.exe -m problem_bridge migrate-revision-history `
  --project outputs/quality_inspection_alignment `
  --project-id quality-inspection-study
```

Migration retains the original JSONL as `revision_history.legacy-v1.jsonl` or `revision_history.legacy-v2.jsonl` and writes `revision_history_migration.json` with the source and migrated hashes. Mixed schemas and records that only pretend to be legacy by changing `schema_version` are rejected.

The rule is unchanged: one stable target receives at most three rounds. After round three, accept it or open a newly scoped target with a consolidated specification; do not append a fourth patch.

## OCR quality gate

OCR reports record engine/version, language, source SHA-256, page locators, page character counts, unavailable confidence status where the engine exposes no calibrated confidence, failed/skipped pages, truncation, and byte/page/character limits. The default gate also applies a 30-second per-operation timeout, renders PDF pages at 150 DPI, and rejects pages above 20 million pixels. Review the report and original source before relying on extracted text.

OCR derives text only. It does not understand charts, figures, diagrams, or image semantics. `derived_text/ocr` cannot satisfy strong-evidence or human-approval requirements by default, and a claim extracted from derived input is routed to `needs_human_review` with `source_inspection` outstanding.

## Synthetic evaluation

Run the offline regression set from the repository root:

```powershell
.venv\Scripts\python.exe scripts\evaluate_gold_set.py --out outputs\synthetic_evaluation
```

The command writes `evaluation_metrics.json` and `evaluation_report.md`, including the gold-set version and SHA-256. In addition to extraction, retrieval, status, miss, and abstention metrics, it reports the rate at which a gold high-risk claim was automatically labelled `supported` or `weakly_supported` instead of being blocked, overclaimed, or sent to human review. This small synthetic set is a regression gate, not a complete gold evaluation or evidence of real-world, biomedical, multilingual, or cross-domain validity.

## Windows install and release gate

First-time or version-change setup:

```powershell
.\scripts\setup_problembridge_windows.ps1
```

Normal daily launch skips dependency installation:

```powershell
.\RUN_PROBLEMBRIDGE_WINDOWS.bat
```

Build and test a clean tracked release in one command:

```powershell
.\scripts\build_and_test_release_powershell.ps1
```

When validating a clean clone that has no repository `.venv` and no usable
`python` command on `PATH`, pass an explicit interpreter without copying it
into the project:

```powershell
.\scripts\build_and_test_release_powershell.ps1 -PythonExe <path-to-python.exe>
```

The release directory contains the ZIP, `<zip>.manifest.json`, and `<zip>.sha256`. The build refuses mismatched `pyproject.toml` / package versions. Its smoke test installs the extracted ZIP source into a new temporary venv under `requirements/constraints.txt`, checks the pinned Typer 0.15.1 / Click 8.1.8 pair, validates sample completion hashes, and runs both demos plus the synthetic evaluation without reusing the repository environment. Release-facing text is normalized to LF by `.gitattributes`.

## Language boundary

The workbench has English and Chinese interface copy. That does not mean the deterministic ClaimHarness audit rules have validated Chinese claim extraction. Current audit rules and the synthetic gold set are English-first. Chinese manuscripts require manual review; Chinese audit support should not be claimed until a versioned Chinese gold set passes explicit gates.
