# 第一轮单人测试：任务材料、提示与观察

这是一份形成性测试建议，尚无真人测试结果。它用于选择后续业务场景、检查首次使用和单方理解，不代替完整双人协作实验。正式业务场景仍在 formative 访谈后确定。

## 找谁

先约 4–6 位可能真正使用系统的人，每次单独进行，作为一轮探索的工作安排，不是效能或饱和度计算。优先找有近期具体工作经历、需要把需求交给其他专业伙伴的人；如果招得到，再包含 1–2 位会整理数据、表格或小程序的技术协作者。记录其角色、相关经验、与软件或 AI 的熟悉程度。第一轮不要求所有人会写代码。

一场只让参与者承担一个真实适合的角色。领域参与者操作 A；技术协作者操作 B。研究者按事先准备的脚本扮演另一方，并明示这是模拟搭档。不要把同一个人连续切换 A/B 的操作统计成双人协作，也不要把研究者熟悉系统带来的帮助当作流程效果。

如果“单人”指总共只能找到一位参与者，就把这次当作试跑：验证材料、脚本和程序是否能走通，记录具体问题，暂不判断普遍学习成本或协作效果。

## 给什么材料

分开准备两张纸。

1. **任务卡：开始时给。** 一页以内，写清身份、使用目的、可用材料、要交出的东西和已知限制，附 3–5 条公开或合成样例。保留一项现实中确需商量的选择；不预设必须改设计，也不为了制造冲突而埋错。任务卡不写按钮名称和点击顺序。
2. **操作速查卡：需要时再给。** 只解释保存草稿、确认版本、切换角色和查看历史。它帮助继续测试，不能替参与者决定业务内容。

参与者用自己的专业经验判断怎样才算有用；研究者负责提供任务边界和可操作材料。既不让他凭空编一个任务，也不先把正确答案和操作路径教给他。若未来产品本来就提供首次引导，应把该引导算作系统的一部分，并记录使用情况。

## 一场约 50 分钟

| 时间 | 做什么 | 得到什么 |
|---|---|---|
| 0–5 分钟 | 说明目的、确认记录许可，强调是在检查产品 | 角色和经验背景 |
| 5–15 分钟 | 请他讲最近一次真实交接：交什么、哪句话没讲清、对方怎么问、后来怎么修正 | formative 场景候选和真实失败点 |
| 15–20 分钟 | 给一页任务卡，让他复述目标；只澄清任务事实 | 识别材料本身是否难懂 |
| 20–40 分钟 | 完成一次对应角色的交接操作，边做边说；研究者按脚本操作另一方 | 找入口、表达理解、回应、查改动和未解决事项的行为 |
| 40–50 分钟 | 独立复述当前决定、变化理由、未解决点和下一步，再回看卡住的地方 | 内容理解与事后解释 |

前面的 10 分钟访谈只用于寻找案例线索，不替代完整 formative 访谈；值得采用的场景仍需进一步追访和确认。

如果本轮尚未确定业务场景，可在试用环节使用容易理解的合成流程练习，先检查操作；访谈中再寻找真实任务。两部分分别分析，不能把练习场景的表现当作专业场景有效性。

## 参与者具体做什么

**领域参与者 A：** 说明并确认需求 → 阅读模拟 B 的理解、建议和问题 → 回应并选择调整或保留需求 → 说明理由、未解决事项与下一步 → 看看返回的小样例是否符合一项要求。

**技术协作者 B：** 阅读预先准备的 A 需求 → 复述理解并提出做法和问题 → 阅读模拟 A 的回应与新版本 → 找出变化和未解决事项 → 判断能否继续，给出依据；有时间再做一个两三行的样例。

模拟搭档脚本应有固定问题和事先写好的分支规则，例如 A 选择“缺失值留空”或“写待确认”时分别如何回应。允许参与者提出新问题；研究者如果临时补答或改变材料，要原样记录，不能事后视作相同测试条件。

## 卡住时怎样帮

先让参与者尝试，自然追问“你现在想完成什么”。明确求助、重复失败，或约 90 秒没有推进时，按同一规则提供最低限度提示：

- 0：无提示完成。
- 1：解释目标或词义，不指出按钮。
- 2：提供速查卡或指出相关区域。
- 3：直接告诉操作步骤，必要时协助操作。

90 秒是本轮建议的主持规则，不是量表标准；试跑后可统一调整。达到直接指导后，记为“辅助完成”，保留此前的无辅助尝试时间，继续观察后面的内容理解。不要把完成时间变短单独解释成协作更好。

## 记录什么

每个关键事件记一行：参与者编号／角色、任务版本、时间、任务步骤、动作或原话、是否正确理解、提示等级、结果、问题类别。类别至少区分界面操作、任务材料、领域知识、理解分歧和程序错误。

重点看：

- 能否找到交接入口，并理解保存草稿与发出回应的区别。
- 能否辨别谁说了什么，以及当前是哪一个版本。
- 能否说出对方建议的含义，为什么采用或不采用。
- 能否准确指出一项变化和一项尚未解决的问题，而非只按“可以继续”。
- 小样例中的问题能否对应到已确认要求。

结束时可问“我能表达自己的设计”和“我能理解伙伴的设计”（0–4 分），但明确这里的伙伴是模拟搭档；结合复述内容解释，不能用自评分单独证明理解。TPACK 只在匹配教学场景与目标人群后考虑；小样本单人测试不做协变量回归。没有实际 AI 参与时，不施测或解释为人机协作体验结果。

## 这轮怎样决定下一步

先修复阻断操作或导致误读版本的地方。若参与者顺利点击却说不清对方改了什么，优先改善回应与变化的呈现；若操作很快但双方话语本来已足够清楚，就检查系统是否增加了额外负担。把这些结果用于改原型、选任务，再安排真实双人测试来检验交接是否帮助双方协调。

任务应给明确、可信的目标而不泄露操作答案，主持人主要观察，必要时帮助恢复推进；这是有主持可用性测试的一般原则。参见 [GOV.UK：Using moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)。上面的招募数量、角色脚本、时长与提示阈值是针对本项目的建议安排。
